PHASE 1 — CHALLENGE ANALYSIS
================================================================================

PROMPT
  Analyse the challenge before writing any code. Do not invent requirements.
  Distinguish HackerRank requirements from recommendations. Produce a 24-hour
  plan, architecture, tech choice, risks, MVP and AI Judge prep.

DECISION
  Split the system in two: the model interprets ambiguous evidence, deterministic
  Python performs every calculation. Reason: six of the seven scored output
  columns are exact-match or categorical. A sampled number is silently wrong some
  fraction of the time with no downstream way to detect it.

DECISION
  Stack: Python 3.11 + stdlib + a hand-rolled tool loop over the Anthropic API.
  Rejected LangGraph and CrewAI. Reasons: the token/cost report is a graded
  deliverable and exact accounting is trivial with a thin wrapper; every line
  must be explainable in the AI Judge interview; the problem needs determinism
  more than orchestration.

IMPLEMENTATION
  None. Analysis only.

PROMPT

  Do not overfit individual requests.

IMPLEMENTATION

  code/calibrate.py— parameter sweep + report

TEST RESULT
  45/45 pass.

TEST RESULT
  864 configurations swept. 3/25 exact, all three CAPPED (label equals
  requested_amount, so the clamp hides the forecast). 0/21 informative exact.
  Best mean symmetric relative error 0.401.

DECISION
  Changed the error metric mid-run. A plain |pred−exp|/exp is asymmetric and
  initially ranked a degenerate all-zero model first. Switched to dividing by the
  mean of the two values, bounding the metric at 2.0 in both directions.

DECISION
  Treated 0/864 as a FALSIFICATION, not a tuning failure. Stopped sweeping and
  went looking for the worst single sample instead.

FINDING (the pivotal one)
  request_05 — one of only six samples with no message and no image, so nothing
  could be hiding in the evidence layer. Predicted 15,488.00 against a label of
  737.00.
  Its last salary credit is described "Final employer payroll". Every prior month
  reads "Payroll credit". Nothing in status, event_type, flexibility or any other
  structured column marks the stream as ended.
  Suppressing projected income for that one sample: 15,488.00 -> 0.00.
  REASON: income continuation is SEMANTIC. It is exactly the judgement the agent
  layer exists to make, which retroactively validates the Phase 1 architecture.

FINDING  The implied outflow (balance − minimum − label) is a WHOLE NUMBER in 16
  of 21 informative samples, while most events carry cents and only the fixed
  commitments are round. Recorded as a lead; not resolved.

PHASE 3-6 — SEMANTIC LAYER, VISION, SOLVER, VALIDATOR
================================================================================

PROMPT
  Implement the semantic layer with a closed enum. Then vision. Then messages.
  Then the full solver, payment plans, validator, output.csv, docs. Execute
  autonomously.

IMPLEMENTATION
  code/evidence.py — income lexicon (39 credit descriptions, a closed
    vocabulary), message classifier, vision extraction, conflict resolution
  code/llm.py      — stdlib urllib client, disk cache keyed by
    sha256(model, purpose, payload), UsageLedger reading response.usage directly
  code/solve.py    — candidates, 6-level ranking, spending changes
  code/explain.py  — fact-pack explanation + deterministic fallback
  code/validate.py — schema, invariants, plan re-simulation, repair
  code/main.py     — pipeline, output.csv, usage report
  code/sweep.py    — scores TOTAL OUTPUT CELLS, not just amount_safe_to_pay
  code/verified_image_amounts.json — all 16 extractions, hand-verified

DECISION
  Built sweep.py because calibrate.py optimises one column while six are scored.
  A forecast can be numerically off and still produce the right decision, so the
  objective that matches the scoring is total cells.

TEST RESULT
  First integrated run: 103/150 cells.

FINDING + IMPLEMENTATION (second pivotal fix)
  Salary streams were grouped by description. The dataset RENAMES a payroll
  stream as the user's situation changes ("Prorated first salary" ->
  "Next confirmed salary"; "Payroll credit" -> "Final employer payroll" ->
  "New employer payroll"). Description-grouping splits one stream into fragments,
  each below the occurrence threshold, so the user's income silently vanishes
  from the forecast.
  Added config.income_group_by_category (default True) and allowed the scheduled
  "Next confirmed salary" row to anchor the forward projection.

TEST RESULT
  Sweep over 288 configs on total cells: best 110/150 with category grouping on.

TEST RESULT
  Finer sweep, 324 configs: 113/150 at recurrence_lookback_days=150,
  recurrence_min_occurrences=3, amount modes median/median,
  monthly_day_of_month cadence.
  Per column: method 25/25, status 22/25, plan 22/25, changes 22/25,
  earliest 18/25, safe 4/25.

DECISION
  Stopped tuning at 113/150. Further gains would have come from nudging the
  affordable_now / affordable_with_plan boundary on three specific samples
  (06, 11, 21), where our headroom is high by 17.10, 599,355 and 31.05. That is
  overfitting to individual requests, which the brief explicitly forbids.

IMPLEMENTATION + REASON
  Validator relaxation. Three of 250 rows paired affordable_with_plan with a
  blank earliest date. That is legitimate: earliest_date_for_full_payment is
  defined WITHOUT optional spending changes, so a plan that only works BECAUSE of
  a spending change can leave it genuinely empty. The 25 samples never exercise
  this. Accepted when a spending change is present, hard-failed otherwise.

TEST RESULT
  Full dataset: 250 rows written, validation PASS, zero exceptions, 0.7s.
  CSV round-trip assertion passes (file reads back identical row-for-row).

ACTION  Built code/analyse.py — per-request error analysis over all 25 samples.
RESULT  18 of 21 informative samples OVER-predict headroom, only 3 under-predict.
REASON  One-directional bias. In Phase 2 errors ran both ways; under the current
        configuration they do not. That points at the set of projected streams,
        not at noise.

ACTION  Tested a hybrid cadence (monthly when the observed median gap is 26-34
        days, observed gap otherwise). Motivation: sub-monthly cadences of 7, 14,
        18 and 21 days appear in nearly every user, and projecting those monthly
        would under-count outflow exactly as observed.
RESULT  113 -> 93. Also tested pure median_gap_days: 93. REJECTED.
REASON  The short-cadence series are many distinct descriptions covering one
        category. A user has eight grocery descriptions each recurring monthly;
        together they are weekly grocery spend. Monthly-per-description already
        gives the right category aggregate. Stepping each at its own gap
        double-counts. Kept `hybrid` in config.py, documented as tested and
        rejected, so nobody repeats the experiment.

ACTION  Added trimmed_mean and recent_median estimators. Swept 360 combinations

        inclusivity.
